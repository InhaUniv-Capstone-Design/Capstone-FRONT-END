# 10. 테스트 및 검증 계획

작성일: 2026-10-31. 수행 기간은 7일이다. 메인 테스터 1명이 앱·서버 시험을 맡고, 하드웨어 실무 테스터 1명이 약통 시험을 같은 주에 병렬로 맡는다. 대상은 Android 앱 `yakyeon-frontend-rebuild`, 개발 서버, DUR 원본과 DB, 약통 실기다. 상세설계서 3장의 요구사항 ID와 5장 (3)의 `NFR-PERF-001`~`006`을 그대로 쓴다. 5장 여섯 지표는 측정 방법만 적고 끝내지 않는다. 일곱 번째 날에 여섯 개 모두 실측값과 통과 또는 실패가 있어야 한다.

이 문서를 쓰는 시점의 통과 여부는 모두 미실행이다. 실행하지 않은 항목에 통과를 적지 않는다.

2026-10-29 문서에는 단위 테스트 140개 통과가 있다. 그 뒤 홈·그래프·약통 계약 테스트가 늘었다. 이 문서 작성 시 `app/src/test`의 `@Test`는 155개, `app/src/androidTest`의 `@Test`는 4개다. 155개를 지금 통과로 적지 않는다. 1일차에 다시 실행한 결과가 공식 기록이다.

## 역할

| 역할 | 인원 | 이번 주 수행 | 하루 |
| --- | --- | --- | --- |
| 메인 테스터 | 1명 | 단위·계측·화면·예외, `NFR-PERF-001`, `002`, `004`, `006` | 약 5시간 |
| 하드웨어 실무 테스터 | 1명 | `NFR-PERF-003`, `NFR-PERF-005` | 약 4시간. 2~6일차 |

메인 테스터가 7일차에 하드웨어 기록지를 받아 10.5 표에 옮긴다. 하드웨어 테스터는 앱 화면 문구 시험을 하지 않는다.

## 시작 전에 갖출 것

5장 시험을 7일 안에 끝내려면 1일차 오전에 아래가 준비돼 있어야 한다. 없는 항목은 1일차에 담당자에게 받고, 그 지표의 실행일은 아래 일정에서 밀지 않는다. 준비 대기만으로 그 지표를 주에서 빼지 않는다.

| 준비물 | 쓰는 시험 | 받는 곳 |
| --- | --- | --- |
| `http://localhost:8080` 가동, 테스트 계정 1개 | L3, PF-01, PF-04, PF-06 | 백엔드 |
| JMeter 5.x, 부하용 계정 100개 또는 계정 생성 방법 | PF-04 | 메인 테스터 설치, 계정은 백엔드 |
| 식약처 DUR 원본 파일, DB 병용금기 관계 내보내기(CSV) | PF-02 | 백엔드 |
| 주민등록번호를 가린 약봉투 사진 10장과 칸별 정답표 | PF-06 | 메인 테스터가 1일차에 정답표를 작성 |
| 약통 1대, 충전, 테스트 폰과 같은 망, 알림 권한 허용 | PF-03, PF-05 | 하드웨어 테스터 |
| 서버에서 칸 번호·버튼·감지 시각을 조회하는 방법 | PF-03, PF-05 | 백엔드가 조회 경로를 1일차에 고침 |

## 이번 주에 하는 일

1. 이미 있는 JVM 단위 테스트 155개를 한 번 실행한다. 새 테스트를 대량으로 추가하지 않는다.
2. 에뮬레이터에서 로컬 데모와 입력 검증 15개, 예외·보안 10개, 서버가 떠 있으면 실서버 화면 8개를 확인한다.
3. 5장 성능 지표 6개를 아래 담당이 모두 실행하고 숫자를 남긴다.

## 이번 주에 하지 않는 일

- 침투 시험, 토큰 탈취, 비밀번호 크랙
- 로그인 잠금. 4-2는 실패 횟수와 잠금 시간을 `확정 필요`로 두었다. 숫자가 생기기 전에는 잠금 케이스를 만들지 않는다.
- 권한 관리 웹의 QR 동의 전체 흐름. 약통 시험의 전제가 아니다.

## 10.1 테스트 전략·환경

### 전략

시험을 다섯 층으로 나눈다. 위 층이 아래 층의 통과를 대신하지 않는다.

| 층 | 이름 | 확인하는 것 | 이번 주 |
| --- | --- | --- | --- |
| L0 | 단위·계약 | 입력 규칙, 복약 규칙, JSON 파서, 오류 코드 분류. 기기와 서버 없음 | 기존 155개 재실행 |
| L1 | 계측 | 에뮬레이터에서 그래프 WebView가 로컬 문서를 읽는지 | `GraphWebRenderTest` 2개 |
| L2 | 수동, 로컬 | 디버그 빌드의 화면 문구, 이동, 저장. 서버 응답이 아님 | 15개 |
| L3 | 수동, 실서버 | 로그인 후 화면이 HTTP 응답으로 바뀌는지 | 8개. 4일차. 서버는 시작 조건 |
| L4 | 5장 성능 | `NFR-PERF-001`~`006` 실측 | 6개 전부. 담당은 역할 표 |

L2에서 홈 개수나 그래프 선이 맞아도 `FR-HOME-001`, `FR-DUR-001`의 서버 동작이 맞은 것은 아니다. 로그인하지 않은 홈·그래프·약통은 로컬 데모다. L2 결과의 관련 요구사항 칸에는 로컬 규칙이라고 적는다.

판정 문구는 다섯 개만 쓴다.

| 문구 | 뜻 |
| --- | --- |
| 통과 | 기대한 화면·값·로그를 실행해서 봤다 |
| 실패 | 환경은 갖춰졌는데 기대와 달랐다 |
| 설계 차이 | 4장 문장과 현재 앱 코드가 다르다. 합격으로 바꾸지 않고 차이만 적는다 |

5장 지표에는 `미측정`을 완료 판정으로 쓰지 않는다. 숫자를 못 재면 그 지표는 실패이고, 막힌 이유와 막힌 시각을 적는다.

로컬 데모 진입은 로그인 화면의 `개발용 홈 보기`다. 홈 인사말을 길게 누르면 `개발용 도구`가 열린다. 약 데이터는 `시나리오 한의원·내과`를 쓴다. 이 데이터는 병원 처방도 DUR 등재도 아니다. 화면에 `개발용`이라고 남아 있어야 한다.

### 끝내는 조건

7일차에 아래가 있으면 이 계획은 완료다. 목표 숫자를 못 넘겨도, 여섯 지표를 실행하고 통과 또는 실패를 적었으면 계획의 수행은 끝난 것이다.

- UT-01~UT-12, IT-01~IT-15, EX-01~EX-10, IT-S01~IT-S08에 판정이 적혀 있다.
- PF-01~PF-06에 실측 숫자와 통과 또는 실패가 적혀 있다. 빈 칸과 `미측정`은 완료가 아니다.

## 10.2 단위 테스트

단위 테스트는 JVM에서 돈다. `SharedPreferences`, WebView, 카메라, 네트워크 소켓을 쓰지 않는다. 서버 JSON을 검사하는 테스트는 저장소에 적어 둔 문자열을 파싱한다. 그 통과는 실서버 통과가 아니다.

이번 주는 파일을 새로 만들지 않고 아래 묶음으로 재실행한다. 한 묶음이 실패하면 그 묶음만 `./gradlew :app:testDebugUnitTest --offline --tests <클래스>`로 다시 돌린다.

| 테스트 ID | 관련 요구사항 | 클래스 | 보는 동작 |
| --- | --- | --- | --- |
| UT-01 | FR-AUTH-001 | `AuthValidationTest`, `AuthFlowTest`, `LatinCredentialFilterTest` | 아이디 6~20자 영문·숫자, 비밀번호 영문·숫자·특수문자 8~64자, 확인 일치, 유형 미선택, 필수 동의, 영문·숫자 이외 입력 제거 |
| UT-02 | FR-AUTH-002 | `AuthValidationTest`, `DevHomeGateTest`, `ApiContractTest` | 아이디·비밀번호가 비면 로그인 불가. 릴리스는 비로그인 홈 불가. refresh token이 있을 때만 로그아웃 요청을 만든다 |
| UT-03 | FR-AUTH-003 | `AuthFlowTest` | 가입 동의 세 항목이 모두 있어야 진행 |
| UT-04 | FR-HOME-001, FR-SCHEDULE-001 | `HomeContractTest` | 홈 요약, 일정, 먹었어요 본문의 필드 이름. 실응답 아님 |
| UT-05 | FR-SCHEDULE-001, FR-SCHEDULE-002 | `MedicationRulesTest`, `ScenarioPrescriptionsTest`, `ClockTimeTest` | 아침·점심·저녁 간격 4시간, 취침 예외, 예정 시각 3시간 안의 수기 보정, 기간 밖 회차 없음. 이 규칙은 로컬 저장소 규칙이다 |
| UT-06 | FR-ADD-002, FR-LIST-002 | `MedicationRulesTest`, `EnvelopePolicyTest`, `MedicineNameCatalogTest` | 확인 전 저장 거절, 약 이름 검색, 종료·삭제가 다른 봉투 기록을 지우지 않음 |
| UT-07 | FR-DUR-001, FR-GRAPH-001 | `DrugRelationsTest`, `DevGraphChecksTest`, `CareContractTest` | 복용 중 약만 노드. 개발용 선은 등재 결과가 아님. 요약 JSON에 등급·점수 필드를 읽지 않음 |
| UT-08 | FR-PILLBOX-003 | `MedicationRulesTest`, `EnvelopePolicyTest` | 사용 중 칸 거절, 빈 칸만 확정, 약통 없이도 등록, 연결 해제 후 약·기록 유지 |
| UT-09 | FR-ALARM-003 | `NotificationSyncTest`, `SettingsStateTest` | 약통 알림을 끄면 하위 항목이 꺼지고, 다시 켜면 끄기 전 값으로 돌아옴 |
| UT-10 | FR-SHARE-001 | `ShareSummaryTest`, `SettingsStateTest` | 공유 기간 7·30·90일만 허용. 현재 복용 약은 포함 |
| UT-11 | FR-AUTH-002, FR-AUTH-005 | `ApiFailureTest` | `INVALID_CREDENTIALS`는 인증 실패. `REFRESH_TOKEN_REUSED`는 세션 종료. 없는 코드의 문구를 만들지 않음 |
| UT-12 | FR-PILLBOX-001 | `DevFixturesTest`, `DevPillboxScenarioGateTest` | 시나리오 약이 칸을 차지하는 방식, 예시 초기화가 확정 약을 지우지 않음 |

`ExampleUnitTest`의 `2+2`는 제품 판정에서 뺀다. 실행에는 포함돼도 UT 표의 통과 조건이 아니다.

절차는 공통이다.

1. 프로젝트 루트에서 `./gradlew :app:testDebugUnitTest --offline`을 실행한다.
2. 콘솔의 `BUILD SUCCESSFUL` 또는 `FAILED`와 XML의 `tests`, `failures`, `errors`, `skipped`를 UT 표 아래에 한 줄로 적는다.
3. 실패가 있으면 실패 메서드 이름과 기대값·실제값 한 줄을 해당 UT에 적는다.
4. 155개 전체를 한 UT의 통과로 합치지 않는다. 그 클래스 묶음이 실패 0이면 그 UT만 통과다.

기대 결과: 각 클래스 묶음이 실패 0, 오류 0이다. 건너뜀이 있으면 통과로 세지 않고 이유를 적는다.

통과 여부: 미실행.

알려진 설계 차이는 실패로 바로 처리하지 않는다. 로컬 규칙은 취침 회차와 3시간 보정, 4시간 예외를 가지고 있다. 서버 명세는 취침을 거절하고 정상·지연·누락을 서버가 계산한다. UT-05가 통과해도 서버 판정이 맞은 것은 아니다. 이 문장은 7일차 기록에 그대로 남긴다.

## 10.3 통합 테스트

화면 통합은 L1, L2, L3다. 약통과 앱을 잇는 통신 시험은 10.5의 PF-03, PF-05에서 하드웨어 테스터가 수행한다.

### L1 계측

| 테스트 ID | 관련 요구사항 | 절차 | 기대 결과 | 통과 여부 |
| --- | --- | --- | --- | --- |
| IT-L1-01 | FR-GRAPH-001 | 에뮬레이터에 debug APK를 설치하고 `GraphWebRenderTest`를 실행한다 | `homeGraphChecksReachTheGraphTab`, `graphWebViewLoadsTheLocalDocument` 실패 0. 노드가 보여도 DUR 등재는 아니다 | 미실행 |
| IT-L1-02 | 해당 없음 | `ExampleInstrumentedTest`는 패키지명만 본다 | 제품 기능의 통과 조건으로 쓰지 않는다. 실패해도 요구사항 실패로 올리지 않고 빌드 문제로만 적는다 | 미실행 |

`GraphWebRenderTest`는 그래프 검증 약을 기기에 남긴다. L2를 시작하기 전에 앱 데이터를 지운다. `adb shell pm clear com.example.yakyeon2`

### L2 수동

공통 준비: 앱 데이터를 지우고 debug APK를 설치한다. 서버에 로그인하지 않는다. 각 케이스의 기대와 다르면 실패, 같으면 통과다. 한 케이스에 10분을 넘기면 그 케이스는 중단하고 본 것까지만 적는다.

| 테스트 ID | 관련 요구사항 | 절차 | 기대 결과 | 통과 여부 |
| --- | --- | --- | --- | --- |

### PF-01 병용금기 매칭 응답속도

절차:

1. JMeter에 스레드 20, 램프업 10초, 반복 1회를 둔다. 이 세트를 3번 실행한다.
2. 각 스레드는 테스트 계정으로 `POST /patients/{patientId}/prescriptions`를 보내고, 그 응답이 끝나면 바로 `GET /patients/{patientId}/interactions/summary`를 보낸다.
3. 한 스레드의 시간은 등록 요청을 보낸 시각부터 요약 응답을 받은 시각까지다.
4. 3세트의 모든 스레드 시간에서 p95를 구한다. p95가 3000ms 이하이면 통과다.
5. 등록에 쓴 처방은 세트가 끝난 뒤 테스트 계정에서 지운다. 지우기 전에 요약 건수를 한 줄 적는다.
6. 홈 화면이 갱신되는 시각은 이 지표에 넣지 않는다. 5장의 검증 방법은 서버 부하 테스트다.

기록: 세트별 성공 스레드 수, p95(ms), 최대(ms).

### PF-02 DUR 데이터 변환 정확도

절차:

1. 원본 파일의 병용금기 관계 수를 A로 적는다.
2. DB에서 받은 CSV의 관계 수를 B로 적는다. 표 이름은 파일을 연 뒤에 적고, 열기 전에 이름을 단정하지 않는다.
3. 관계 키는 원본과 CSV에 같이 있는 약물 식별자 쌍으로 한다. 키가 같은 행에서 금기 내용이 같은 수를 C로 센다. 비교는 스크립트로 하고, 끝난 뒤 행 10개를 눈으로 다시 봐 스크립트와 맞는지 확인한다.
4. 정확도 = C / A. 0.99 이상이면 통과다.
5. A와 B가 다르면 차이 건수를 같이 적는다. 앱 화면의 선 개수로 이 값을 대체하지 않는다.

기록: A, B, C, 정확도, 눈으로 본 10건 중 스크립트와 어긋난 수.

### PF-03 움직임 감지·버튼 입력 기록 정확도

담당은 하드웨어 실무 테스터다. 칸 1, 칸 2, 칸 3을 각각 100회 한다. 합계 300회. 1일차 예비 5회는 횟수에 넣지 않는다.

한 회의 순서:

1. 그 칸에서 IR 움직임 감지가 되게 한다.
2. 그 칸의 버튼을 누른다.
3. 서버 조회에서 같은 회의 칸 번호, 감지 시각, 버튼 시각이 있으면 성공이다. 하나라도 없으면 실패다.
4. 약을 먹었는지는 보지 않는다.

칸 속도는 1시간에 50회를 기준으로 한다. 한 칸은 휴식 포함 약 2시간 30분이다. 하루 한 칸이다.

기록지 열: 회차, 칸, IR 감지 여부, 버튼 여부, 서버 반영 여부, 메모.

기대 결과: 칸마다 성공이 95회 이상. 세 칸이 모두 넘으면 통과다.

절차:

1. JMeter에 스레드 100, 램프업 30초, 반복 1회를 둔다. 한 스레드가 보호자–복약자 한 쌍이다.
2. 각 스레드는 로그인 1회 후 `GET /patients/{patientId}/home-summary` 1회만 한다. 등록 요청은 PF-01에서 이미 했으므로 여기서 반복하지 않는다.
3. 홈 요약의 p95가 1000ms 이하이면 통과다.
4. 계정 100개를 만들기 어려우면 백엔드가 내준 부하용 계정 목록을 쓴다. 계정 하나를 100스레드가 나누어 쓰는 결과는 이 지표의 통과로 적지 않는다.
5. 6일차에 실행한다. PF-01 스크립트와 파일을 분리한다.

기록: 스레드 100, 로그인 성공 수, 홈 요약 p95(ms), 오류 수.

### PF-05 약통–앱 동기화 지연

담당은 하드웨어 실무 테스터다. 실기기에서 30회 한다. 칸마다 10회다. PF-03의 300회와 시간을 섞지 않고 5일차에 따로 한다.

한 회의 순서:

1. 시험 전에 약통 시계와 폰 시계를 맞춘다. 차이가 1초를 넘으면 맞춘 뒤에 시작한다.
2. 버튼 시각을 T0, 폰에 알림이 보인 시각을 T1으로 적는다. 초 단위로 읽고, 차는 초로 적는다.
3. T1−T0가 5초 이하이면 그 회는 성공이다.
4. 알림이 없고 약통 화면 문구만 바뀌면 그 회는 실패다. 화면 시각을 알림 시각으로 적지 않는다.

기대 결과: 30회가 모두 5초 이내이면 통과다. 넘긴 회차의 초를 기록지에 남긴다.

### PF-06 약봉투 OCR 처리

5장은 처리 시간과 인식 정확도의 숫자 목표를 엔진 비교 뒤로 미뤘다. 이번 주에 하는 일은 샘플 대조를 끝내고, 그 결과로 목표 숫자 초안을 한 줄 적는 것이다.

절차:

1. 가린 약봉투 10장의 정답표를 1일차에 만든다. 칸은 약물명, 복용량, 1일 횟수, 복용 시점, 복용 기간이다. 주민등록번호가 보이는 장은 빼 교체한다.
2. 프로젝트에 연결된 OCR 후보마다 같은 10장을 한 번씩 보낸다. 장마다 요청부터 응답까지의 ms와 다섯 칸의 맞음 여부를 적는다.
3. 후보별 정확도 = 맞은 칸 / 50. 처리 시간은 10장의 중앙값이다.
4. 후보가 둘 이상이면 정확도가 높은 쪽을 고르고, 그 중앙 시간과 정확도를 목표 초안으로 적는다. 둘 다 적었으면 통과다.
5. 연결된 후보가 하나이면 그 엔진의 중앙 시간과 정확도를 적고, 비교 대상이 하나뿐이라는 사실과 함께 목표 초안으로 남긴다. 샘플 10장을 모두 대조했으면 통과다. 목 응답만 있고 정답과 칸을 비교하지 않았으면 실패다.

기록: 후보 이름, 장 수 10, 중앙 시간(ms), 정확도, 목표 초안 한 줄.
